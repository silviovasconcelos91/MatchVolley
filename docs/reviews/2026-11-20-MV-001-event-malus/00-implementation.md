# Implémentation — MV-001 event `malus` (validation, overlay, analyse)

## Intention
Le front envoie un event `malus` (handicap de début de set : `team` = équipe pénalisée, `malusAmount` ∈ {1, 2}, sans joueur, sans trajectoire, sans `scoredFor`). Le backend doit l'accepter (validation du snapshot), le déduire de tous les scores qu'il recalcule (overlay public, timeline et temps morts de l'analyse) et l'exclure de tout ce qui n'est pas un score (service, derniers points, meilleurs marqueurs, stats d'actions). L'analyse expose en plus un `startScore` par set (décision Q1). Pas de migration : les events sont en `jsonb`.

## Choix de conception
- **Le malus est appliqué comme un score de départ, pas en parcourant les events** (`LiveStatsPayloadValidator.malusOf(events, team)`, puis `mine = -malusOf(..)` avant la boucle). **Pourquoi** : la règle métier valide fait du malus un handicap *antérieur* à tout point (CA-6). Score de départ et décrément « au fil de l'eau » donnent donc le même résultat. Le score de départ a deux avantages : il ne dépend pas de l'ordre de la liste, et il donne directement `trajectory[0]` (CA-10) et `startScore` (CA-18). C'est important pour l'analyse, dont `buildTimeline`/`buildTimeouts` parcourent les events dans l'ordre **stocké** (pas trié par `sequence`, cf. javadoc existante). Un payload désordonné (malus listé après un point mais de `sequence` inférieure, accepté par CA-6) aurait sinon une timeline fausse. Test dédié : `LiveStatsAnalysisServiceTest#should_deductMalus_in_timeline_when_events_are_not_in_sequence_order`. Alternative écartée : décrémenter dans la boucle (le plan du ticket). Elle est équivalente dans l'overlay, qui trie par `sequence`, mais fausse dans l'analyse sans tri préalable.
- **`isMalus` / `malusOf` dans `LiveStatsPayloadValidator`**, à côté de `isTimeout`. **Pourquoi** : c'est le pattern posé par le commit timeout (`isTimeout` statique package-private, utilisé par `LivePublicViewService` et `LiveStatsAnalysisService`). Alternative écartée : une classe utilitaire `LiveEvents`. Elle serait plus propre à terme, mais elle déplacerait `isTimeout`/`MINE`/`OPP`, une refactorisation hors périmètre.
- **`isMalus` se base sur `action.key == "malus"`** (comme `isTimeout`). La cohérence `key` ⇔ `category` est imposée par la validation dans les deux sens (CA-4). Un `category: "malus"` avec une autre clé est rejeté explicitement **avant** les autres contrôles, pour un message clair plutôt que « player.jersey is required ».
- **Ordre des contrôles d'un event non-malus** : `malusAmount != null` → 400 avant tout autre contrôle, y compris pour un temps mort (CA-3).
- **Placement : `sequence` du malus strictement inférieure à la plus petite `sequence` d'un event scorant** (`validateMalusPlacement`, après la validation unitaire des events). **Pourquoi** : CA-6 évalue l'ordre par `sequence`, pas par position. À `sequence` égale, le malus est rejeté. Le ticket ne tranche pas ce cas, car les `sequence` sont censées être uniques. Accepter l'égalité laisserait l'ordre indéterminé. Coût : un passage de plus sur les events du set (O(n), n ≈ 50 à 100 events par set).
- **Overlay : `continue` sur un malus avant `activeTimeout = null`**. **Pourquoi** : décision H3, un malus ne termine pas un temps mort actif. Test `should_keep_active_timeout_when_malus_follows_timeout`.
- **Analyse : `afterPoint` passe sur un compteur `pointsPlayed` dédié**, au lieu de `myScore + oppScore`. **Pourquoi** : avec un malus, la somme des scores n'est plus le nombre de points joués (CA-15, risque listé dans le ticket).
- **Nouveau record `LiveScoreDto(int myScore, int oppScore)`** pour `startScore`. **Pourquoi** : le ticket demande `{myScore, oppScore}`, le nommage de l'analyse. `ScoreDto(mine, opp)` est le nommage de l'overlay (package `livesession`), et `TimelineEntryDto` porte d'autres champs. `startScore` est ajouté **en dernier composant** de `LiveSetAnalysisDto`, comme `timeouts` l'avait été, ce qui donne un diff minimal.
- **`malusAmount` ajouté en dernier composant de `LiveEventDto`**, sans constructeur secondaire. Tous les `new LiveEventDto(...)` (tests uniquement) ont été mis à jour. **Pourquoi** : c'est le plan du ticket, et Jackson 3 désérialise un champ absent en `null`, ce qui assure la rétrocompatibilité des snapshots et `MatchLiveSetEvent.events` déjà stockés (CA-8).
- **Pas de recalcul de `scoreTeam`/`scoreOpp` au POST** (H1) : la sauvegarde est inchangée.
- **Native image** : aucun hint ajouté. `LiveEventDto` reste couvert par `BindingReflectionHintsRegistrar` sur `LiveStatsRequest` (`NativeConfig.java:30`). `LiveScoreDto` est un DTO de réponse de controller, au même titre que `LiveTimeoutDto` ajouté par bd673c1 sans hint.

**Écart à arbitrer (CA-2 à CA-7, côté POST)** : le ticket présente `LiveStatsPayloadValidator` comme « commun à `POST /matches/{id}/live-stats` et `PUT /live-sessions/{id}/snapshot` ». C'est **faux dans le code actuel** : le validateur n'est appelé que dans `LiveSessionService.java:95` (PUT snapshot). `LiveStatsController.saveLiveStats` et `LiveStatsService.saveLiveStats` ne valident pas le payload. C'est le cas depuis l'introduction du validateur (76f5285), qui ne visait que les sessions live. Je l'ai constaté parce qu'un premier test IT « POST malus invalide → 400 » a reçu 201. Les 400 de CA-2 à CA-7 sont donc prouvés sur PUT (unitaires + IT), **pas sur POST**. Je n'ai pas branché le validateur sur POST : ce serait durcir un endpoint existant pour **toutes** les règles (setNumber, scoredFor, jersey…), pas seulement le malus. Cette décision a été prise sur une prémisse erronée (« le POST final échoue »), et elle risque précisément le dommage que le ticket veut éviter : un match non sauvegardé. Si l'humain le souhaite, le correctif tient en 2 lignes : injecter `LiveStatsPayloadValidator` dans `LiveStatsService` et appeler `validate(request)` en tête de `saveLiveStats`. Il faudrait ensuite un IT POST 400. Corollaire : la phrase du ticket « le `POST` final échoue (match non sauvegardé) » est également fausse. Avant ce ticket, le POST acceptait déjà le malus (201). Seuls l'overlay (PUT 400) et l'analyse (27-15) étaient touchés.

## Points d'attention
1. **POST non validé** (voir l'encadré « Écart à arbitrer » plus haut) : décision humaine requise, soit brancher le validateur sur POST, soit corriger le ticket et la doc. La doc reste juste en l'état : les règles de validation 400 ne figurent que dans la section PUT de `live-overlay-api-doc.md`.
2. **`./mvnw test` n'exécute pas les tests d'intégration.** Le `pom.xml` ne configure pas surefire : les includes par défaut (`**/*Test.java`, `**/Test*.java`, `**/*Tests.java`, `**/*TestCase.java`) excluent `*IT`. CLAUDE.md affirme le contraire (« tous les tests (unitaires + *IT) »). Conséquence : `DataIsolationIT` et tous les `*IT` ne tournent que si on les cible explicitement. La CI ne les rattrape pas : `.github/workflows/build.yml` ne lance aucune commande de test, seulement le build et le push de l'image Docker. Je n'ai pas modifié `pom.xml` (interdit sans demande). J'ai lancé les IT explicitement avec `-Dtest='*Test,*IT'`. À arbitrer : soit configurer surefire/failsafe, soit corriger CLAUDE.md.
3. **Build natif non vérifié** localement. Analyse : composant ajouté à un record déjà couvert par `BindingReflectionHintsRegistrar(LiveStatsRequest)`, nouveau record de réponse sur le même modèle que `LiveTimeoutDto`, pas de nouvelle réflexion, Jackson 3 inchangé.
4. **`sequence` égale** entre un malus et un premier event scorant → 400 (interprétation stricte de « avant », non précisée par le ticket).
5. **Données incohérentes déjà stockées** : `malusOf` ignore un `malusAmount` null et n'applique aucun plafond. Un malus invalide stocké par le POST non validé (point 1), par exemple `malusAmount: 5`, donnerait un `startScore` de -5 dans l'analyse. Ce cas est impossible côté overlay, car le PUT valide.
6. **Front** : `SetGraph.tsx` part de `{0,0}` en dur. Il doit utiliser `startScore` (documenté dans `live-stats-analysis-api-doc.md`, hors périmètre backend).
