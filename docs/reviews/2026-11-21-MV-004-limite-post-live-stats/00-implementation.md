# Implémentation — MV-004 : limiter à 1 Mo le corps de POST live-stats

## Intention
`POST /api/v1/matches/{matchId}/live-stats` n'avait aucune limite de taille : un compte authentifié pouvait faire désérialiser des centaines de Mo en mémoire (risque d'OOM sur l'image native Railway). La demande applique au POST la limite de 1 Mo (413, enveloppe `ApiResponse`, rien de persisté) déjà en place sur `PUT /live-sessions/{id}/snapshot`. Elle étend le filtre existant sans le dupliquer et laisse les autres endpoints hors filtre.

## Choix de conception
- **Extension du filtre existant, renommé `SnapshotBodySizeFilter` → `LivePayloadSizeFilter`.** **Pourquoi** : CA-7 autorise le renommage. L'ancien nom et son message (« Snapshot exceeds 1 MB ») décrivaient un seul endpoint et seraient devenus faux. Les deux routes filtrées transportent le même contrat de payload live (`LiveStatsRequest`, même validateur, MV-001 Q4), d'où le nom. Je n'ai pas créé de deuxième filtre ni de classe abstraite : un seul `MAX_BYTES` et un seul `LimitedInputStream`. Alternative écartée : garder le nom. Le diff aurait été plus petit, mais le nom aurait menti sur le périmètre. Aucune autre référence au nom de classe sous `src/` (bean détecté par `@Component`, aucun hint natif ni config ne le cite).
- **`shouldNotFilter` reçoit un deuxième couple (méthode, regex)** : `POST` + `^/api/v1/matches/[^/]+/live-stats$`. **Pourquoi** : c'est le style du code existant (regex précompilée sur `getRequestURI()`). La regex exclut `/live-stats/analysis` et les chemins à plusieurs segments. Méthode et chemin sont tous deux exigés, donc `GET /matches/{id}/live-stats` n'est pas filtré (CA-6). Alternative écartée : un `AntPathMatcher`/`PathPattern`. Ce serait plus lisible à 5+ routes, mais c'est inutile à 2 routes, et la décision Q1 exclut d'étendre à d'autres endpoints.
- **Message rendu générique : « Request body exceeds 1 MB »**, identique pour les deux routes. **Pourquoi** : le ticket (Impacts) demande un message générique ou dépendant du chemin. Le générique évite une branche et une deuxième chaîne JSON écrite à la main. Le front distingue déjà l'endpoint appelé. L'ancien message n'était documenté nulle part (`live-overlay-api-doc.md:188` ne mentionne que « Body > 1 Mo »), donc le changement ne casse pas le contrat.
- **Enveloppe JSON toujours écrite à la main dans le filtre pour le cas `Content-Length`.** **Pourquoi** : c'est le comportement existant. Un filtre servlet s'exécute hors du `DispatcherServlet`, donc `GlobalExceptionHandler` ne s'applique pas. La chaîne est une constante sans caractère à échapper. Le cas chunked passe, lui, par `PayloadTooLargeException` → `GlobalExceptionHandler` (413 enveloppé), car l'exception est levée pendant la lecture du corps par Jackson, dans le contrôleur. Les IT vérifient les deux chemins et obtiennent la même enveloppe.
- **Ordre des filtres inchangé.** Le filtre est un `@Component` sans `@Order` (donc `LOWEST_PRECEDENCE`), placé après la chaîne Spring Security (ordre -100). **Pourquoi** : un appel sans JWT est rejeté en 401 avant toute lecture du corps, ce qui est le meilleur cas pour CA-5. Le firewall Spring Security (`StrictHttpFirewall`) rejette déjà `;`, `//` et `..` dans l'URI avant le filtre : la regex ne peut pas être contournée par ces variantes de chemin.
- **Pas de modification de `application*.properties` ni de `pom.xml`, pas de dépendance, pas de hint natif.** Aucune réflexion nouvelle. Côté test, `java.net.http.HttpClient` (JDK) envoie le corps chunked, et `tools.jackson` (déjà présent, Jackson 3) relit l'enveloppe et mesure la taille des fixtures.

Lecture de CA-5 : le CA accepte « 401 ou 413 ». Le test l'assert tel quel (`isIn(401, 413)`) et vérifie en plus que rien n'est persisté. Avec l'ordre actuel des filtres, la réponse attendue est 401 (sécurité avant taille).

## Tests
- `LivePayloadSizeFilterTest` (15 cas) : routage `shouldNotFilter` (2 routes filtrées, 10 non filtrées), rejet anticipé sur `Content-Length` (enveloppe exacte, chaîne non appelée), borne 1 Mo pile acceptée, flux chunked qui lève `PayloadTooLargeException` au-delà de 1 Mo.
- `LiveStatsControllerIT`, 5 nouveaux tests : 413 sur `Content-Length`, 413 en chunked, 201 réaliste 5×100, 201 extrême 10×300, sans JWT → 401/413. Les 3 tests de rejet vérifient l'absence en base et le `GET` → 404.
- Cycle TDD : avant la modification du filtre, les 2 IT 413 échouaient avec **500** (pas 413 : le POST surdimensionné finissait en erreur serveur, cause non investiguée, peut-être le titre de 1 Mo en base) et 3 tests unitaires échouaient. Tout passe après la modification.
- Mesure (règle métier du ticket « ~300 octets/event, ~3 000 events ») : la fixture réaliste (ids `ev-<ts>-<hash>`, timestamps 13 chiffres, noms composés, labels FR, trajectoires) donne **~317 octets/event** (594 o pour 1 event + enveloppe, 158 845 o pour 5×100, 794 091 o pour 10×250, 953 101 o pour 10×300). Le cas extrême 10 sets × 300 events garde donc ~9 % de marge sous 1 Mio. Estimation du ticket confirmée **pour cette fixture** : c'est une estimation (mesurée avec un `JsonMapper` Jackson 3 par défaut), pas la mesure d'un export réel du front, qui peut sérialiser plus ou moins de champs (voir CRIT-004).
- Résultat `./mvnw test` : `Tests run: 288, Failures: 0, Errors: 0, Skipped: 0` — `BUILD SUCCESS`

## Points d'attention
- **Build natif non vérifié localement.** Aucun risque identifié : pas de réflexion, pas de JSON (dé)sérialisé à la main ajouté, le bean renommé est découvert par AOT comme avant. Le `-Pnative` n'a pas été lancé.
- **Marge estimée à ~9 % sur le pire cas (3 000 events), mesurée sur une fixture et non sur un payload réel du front.** Si le front ajoute des champs par event, la marge diminue. Pour une sauvegarde finale, un 413 ferait perdre le match. Le comportement du front sur un 413 est hors périmètre (ticket, Risques), mais à vérifier avant déploiement.
- **Corps chunked sans JWT** : rejeté en 401 par Spring Security sans lecture du corps. Tomcat ne « vide » ensuite que jusqu'à `maxSwallowSize` (2 Mo par défaut) puis ferme la connexion. Le client peut alors voir un reset au lieu du 401 sur un très gros envoi. Cela ne mène jamais à 500 ni à 201, donc ne contredit pas CA-5. Ce cas n'est pas testé au-delà de ~1,03 Mo.
- **Lecture partielle avant rejet chunked** : jusqu'à 1 Mo est lu et tamponné par Jackson avant le 413. C'est le comportement voulu, borné.
- **Renommage** : `docs/reviews/2026-11-20-MV-001-event-malus/r2-reponse.md` et le ticket citent encore `SnapshotBodySizeFilter`. Ce sont des documents historiques que je n'ai pas modifiés.
- Le message 413 du PUT snapshot passe de « Snapshot exceeds 1 MB » à « Request body exceeds 1 MB ». Il n'est documenté nulle part. Si l'overlay ou le front comparait ce texte (peu probable), il faut l'adapter.

## Errata (round 1, voir `r1-reponse.md`)
- Ligne « Ordre des filtres… la regex ne peut pas être contournée » : **faux**. Un encodage `%61` passait le firewall et Spring MVC le routait quand même (CRIT-001). Le matching se fait désormais avec `PathPattern` sur le chemin décodé (sémantique Spring MVC). Cela remplace aussi le choix « regex plutôt que PathPattern » de la section Choix de conception.
- Ligne « Cycle TDD… 500 non investigué » : la cause était la fixture (titre de plus d'un million de caractères dans `matches.title VARCHAR(255)`, CRIT-002/003). La fixture est maintenant un match valide et persistable, gonflé par ses events.
- Résultat `./mvnw test` : 288 tests au round 0, mais exécutés avec un `SnapshotBodySizeFilter.class` périmé resté dans `target/classes`, donc encore actif. Après `./mvnw clean test` au round 1 : voir `r1-reponse.md`.
